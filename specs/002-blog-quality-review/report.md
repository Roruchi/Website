# Blog quality review

Reviewed 2026-11-16. Scope: all 18 Markdown posts in `src/blog/`, not just published articles. Only the playgrounds article was edited. This is an editorial assessment of repository sources, not a claim that every external source or the live website was audited. No publication, crossposting, date change or ledger update is part of this work.

## Rubric

Five dimensions, each 0–4, summed to **/20**. These are judgments with evidence, not a statistical quality measure. Use **0** for absent/unusable, **1** for an outline or major unresolved weakness, **2** for developed but needing substantive work, **3** for sound with a specific remaining improvement, and **4** for strong execution appropriate to the article's purpose. A serious factual or technical blocker takes priority over the total. There is no automatic publish threshold.

| Dimension | What earns a strong score | Evidence in this corpus |
| --- | --- | --- |
| **V: Voice and ownership** | An identifiable author takes a position, admits tension or limits, and avoids generic advice. First-person experience where appropriate; never fabricate experience. | *The Lotus on Stage*: the practice proposal, nerves, and admission that returning to the stage is still scary. *Showing myself*: adaptive planning fails about half the time. *Engineering Discipline*: two teams sharing a repository. |
| **A: Arc and economy** | Opening establishes tension; sections develop rather than repeat it; ending returns to the question or offers an action. Length serves the argument. | *Lotus* moves from a scene through the training insight to “What is your mud?” *Finding Balance* connects grip, compass and worthiness. *Lint the Spec* develops one ambiguous requirement through a working gate and ends on the input-quality argument. |
| **C: Concrete usefulness** | A scene, example, artefact or exercise makes the abstract idea inspectable and gives the reader something to consider or try. | The eight students in *Inner Critic*, pen exercise in *Finding Balance*, before/after requirement and YAML rule in *Lint the Spec*. A reflection need not include code or a checklist. |
| **T: Trust and claim boundaries** | Clearly distinguish personal observation, metaphor, imagined scenario and externally checkable fact. Attribute borrowed ideas and qualify unsupported generalisations. | *Lint the Spec* explicitly does not claim improved software yet. *Whitepaper* distinguishes API-equivalent estimates from an actual bill. Some older articles do less well here; their unsupported numbers are not a standard to imitate. |
| **P: Presentation and readiness** | Complete valid metadata; readable headings and links; useful images with text alternatives; appropriate related content and clear distribution state. | All posts have title, description, date, pillar and tags. Modern posts use `relatedTalks: []`; imports often omit it. *Lint the Spec* has descriptive image alternatives and a named playground link. Imported HTML often starts at h3 and has empty alt text: existing defects, not conventions to copy. |

Published articles span approximately **611–1,632 body words** by the method below. This is descriptive, not a required range. The 271–340-word idea briefs explicitly defer evidence or development. At 965 words the edited playgrounds piece fits its scope; padding it to match the longest article would weaken A.

Images/covers are present in every published post in this snapshot, so a useful local diagram brings playgrounds closer to those examples. Multiple images, a `cardCover`, a fixed number of headings, internal links and nonempty related talks are not universal requirements. Do not invent a talk relationship or add an irrelevant illustration for points. Relevant internal links are useful when they extend the argument, as in the perfectionism series.

The script's environment override is an execution guard, not evidence that deployment happened.

For the later publication decision:

1. Publish the website article first and confirm its live URL. On that separate occasion, change `status: draft` to `status: published`; if a legacy `draft` field is present it must be absent or Boolean `false`. Either `status: draft` or `draft: true` blocks the extractor, regardless of the date. Retain a nonempty title/body and valid article metadata (description, date, engineering pillar and taxonomy-approved tags including `post`); no extra crosspost-specific slug or canonical frontmatter field is required by the extractor. This task leaves status and date unchanged.
2. Keep `originalUrl` absent or empty for this original article. A nonempty `originalUrl` makes the Medium target skip it as an imported original. Do not add the future website URL to `originalUrl` to request a canonical link: the extractor uses that field for exclusion, not Medium canonical configuration.
3. Make the opt-in tag agree with `CROSSPOST_MEDIUM_TAG`, whose default is `crosspost-medium`. **Mismatch:** that default tag is absent from the current taxonomy and would make content validation fail if added now. Resolve this separately before the actual crosspost: either authorize that tag in the taxonomy, or deliberately set the existing override to an already valid tag on this article. The latter should use this exact source path, not a broad glob that opts other engineering posts in. Neither the taxonomy nor this article's tags were changed here.
4. Use the existing Medium authentication setup for the later manual run (`MEDIUM_STORAGE_STATE_PATH` or `MEDIUM_STORAGE_STATE` as described in the quickstart). No credentials were read or configured for this task. Invoke only `--platform medium`, with `CROSSPOST_ALLOW_MANUAL=true`, the exact article source and a release identifier. For example, **only after** publishing and resolving the default-tag mismatch, replace `WEBSITE_RELEASE_ID` with the relevant release identifier and use:

   ```bash
   CROSSPOST_ALLOW_MANUAL=true node scripts/crosspost/publish.js --source src/blog/good-architects-build-playgrounds-not-cages.md --platform medium --release-id WEBSITE_RELEASE_ID
   ```

   If choosing the valid-tag override instead of the default-tag fix, add the scoped environment setting `CROSSPOST_MEDIUM_TAG=software-engineering` to that later invocation; this tag already exists on this article. These are future instructions, not commands executed during the review. The script does not fetch the live website to prove it exists.
5. The adapter prepares a **Medium draft**, returning `prepared` / `awaiting_manual_publish`; it does not make the final publish decision. Open that draft, check title/body, links, image alternatives, canonical attribution to the live website article, and publish manually only when satisfied. The adapter does not configure a canonical URL. Successful/prepared article-platform pairs are blocked by the ledger on rerun, even with a new release identifier: use the existing prepared draft rather than trying to republish blindly. No ledger mutation is needed just to assess readiness.

**Formatting mismatch to inspect before that future Medium draft is postable:** `buildMediumBodyHtml` escapes the description but appends `bodyMarkdown` directly and inserts it as HTML; it does not convert Markdown headings, links or images, make root-relative URLs absolute, upload the local SVGs or convert them to raster images. Consequently, eligibility is not a guarantee of formatted long-form fidelity. Review and repair the resulting Medium draft manually, or separately fix the converter before relying on automated fidelity. The current SVGs and internal `/blog/.../` links work on this website; they must be checked/adapted for Medium. No claim of external-platform rendering verification is made.
